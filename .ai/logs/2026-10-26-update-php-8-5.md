# 2026-10-26 — Update PHP version to 8.5.x

## Summary

Moved the `builder` and `base` stages from `docker.io/library/php:8.4-fpm` to
`docker.io/library/php:8.5-fpm` (installed: **PHP 8.5.12**) and raised the `composer.json`
platform floor from `>=8.2` to `>=8.5`. Fixed the one PHP 8.5 deprecation raised by app code.
No package versions changed; extensions, ini/FPM config and runtime behaviour are as on 8.4.

## Changes

- **`Dockerfile`** — both `FROM` lines bumped to `php:8.5-fpm`. Nothing else.
- **`composer.json`** — `"php": ">=8.5"`. The old `>=8.2` was already inaccurate:
  `doctrine/instantiator` 2.1.0 in the lock requires `^8.4`.
- **`composer.lock`** — `composer update --lock`: only `content-hash` and `platform.php` changed.
- **`src/Service/HttpFetchService.php`** — replaced the magic `$http_response_header` local
  (deprecated in 8.5) with `http_get_last_response_headers()`, preceded by
  `http_clear_last_response_headers()`. The new function returns process-wide state, so the
  clear keeps the old semantics: headers are only taken from *this* request's response.
- **`config/routes/framework.yaml`, `config/routes/web_profiler.yaml`** — dev route imports
  switched from `errors.xml` / `wdt.xml` / `profiler.xml` to the bundles' `.php` equivalents,
  removing the Symfony 7.3/7.4 routing deprecations (XML route config is deprecated in 7.4).
  Not a PHP 8.5 issue; done on request while on this branch. Same 17 routes; `/_wdt/{token}`,
  `/_profiler/{token}` → 200, `/_error/500` renders the preview; zero deprecations logged after
  `cache:clear`.
- **`.dockerignore`** — added (extending a local one that only had `vendor/`): excludes
  `vendor/`, `var/`, generated `public/` assets, `docker/nginx/` (incl. `.htpasswd`), `.git/`,
  `.ai/`, `.claude/`, tests and build/compose files. `.env` and `docker/php/` stay in the
  context (`dump-env prod` and the config `COPY`s need them). Previously the prod image carried
  the local dev `vendor/` (phpunit, web-profiler, debug-bundle, dev autoloader), 90 Dropbox
  conflicted-copy files, a dev cache, `.git` and `.htpasswd`; now none of these.
- **`Dockerfile`** (prod) — `composer dump-env prod` moved **before** `asset-map:compile`.
  With `vendor/` excluded the build failed: `.env` sets `APP_ENV=dev`, so the compile booted the
  dev kernel and needed `DebugBundle`, which `--no-dev` doesn't install. It had only worked
  because the local dev `vendor/` was being copied in. Assets now compile in prod (also gone:
  the "Debug mode is enabled" build warning; cache is `var/cache/prod` only). Verified:
  `--no-cache` build, both routes + compiled CSS 200 via nginx with identical response sizes,
  `about` prod / debug false / OPcache Enabled; dev build and `/locate/` still 200.

## Verification (both stacks built and run)

- **Dev** (`docker-compose-dev.yml`, `build --pull`) — `php -v` 8.5.12; `intl`, `zip`,
  `Zend OPcache` loaded; `opcache.enable` Off; `php --ini` clean; `composer validate` OK;
  `bin/console about` → Symfony 7.4.21 / PHP 8.5.12; `cache:clear` OK. `GET /locate/` → 200;
  `GET /autocomplete/en/?query=dengue` → 200 with live DeCS data; JSONP `&callback=cb` intact.
  No PHP deprecations in today's `dev.log`.
- **Prod** (`make build_update_php`, then `docker-compose.yml` + nginx under a throwaway
  compose project with fresh volumes) — `php-fpm -t` OK, no startup warnings;
  `opcache.enable` On, `memory_consumption` 128; `about` reports OPcache Enabled. Both routes
  200 through the FastCGI socket (`/var/run/php-fpm.sock`, `0666`), compiled asset 200, no
  warnings/errors in container logs. `cache:clear` in prod emitted no deprecation after the fix.
- `HttpFetchService` exercised directly: 200 and 404 status codes read correctly; a DNS failure
  returns `false` and keeps the previous headers (unchanged pre-existing behaviour).

## Findings

- **OPcache is compiled statically in 8.5** and the `php:8.5-fpm` image no longer ships
  `conf.d/docker-php-ext-opcache.ini`, so there is no duplicate-load warning and the Dockerfile
  workaround anticipated in the plan was not needed. `opcache.enable` in the project ini files
  still governs on/off.
- The plan's deprecation grep missed `$http_response_header`; it surfaced as a logged
  deprecation during prod `cache:clear` (container warm-up hits `HttpFetchService`).
